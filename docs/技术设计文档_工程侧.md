# 技术设计文档（工程侧）

> 配套：本文与《剧本 YAML Schema 设计文档》（数据模型）、《产品文档》互补。

## 1. 系统架构总览

```
┌──────────────────────────────────────────────┐
│  Browser (Next.js / React)                     │
│  导入 → bible 确认 → 逐章转换 → YAML 编辑/导出  │
│  逐章编排 + assemble + 渲染都在客户端           │
│  状态/作品库/版本/断点 → IndexedDB（无后端账户） │
└──────────────────────┬───────────────────────┘
                       │ fetch（逐章 POST）
┌──────────────────────▼───────────────────────┐
│  Next.js API Routes (服务端)                    │   ← LLM key 只在这层，不进浏览器
│  extract-bible / convert-chapter / update-summary
│  lib/pipeline · lib/llm（限速 + 错误脱敏）       │
└──────────────────────┬───────────────────────┘
                       │
              ┌────────▼─────────┐
              │ LLM Provider      │
              │ DeepSeek（OpenAI  │
              │ 兼容，function-   │
              │ calling 出 JSON） │
              └──────────────────┘
```

**为什么是这个形状**：
- **单仓库 Next.js（全栈）**：前后端同仓，API routes 跑服务端 LLM 调用——**API key 绝不进浏览器**，这是硬要求。
- **无后端 DB / 账户**：单用户持久化全落客户端 **IndexedDB**（作品库 + 版本快照 + 转换断点），省掉整块后端与鉴权。
- **渲染在客户端**：YAML/Screenplay → 各格式文本是纯函数，无需后端（呼应内容/格式分离）。

> 关系型 DB（Postgres/Supabase + Auth）是面向"多用户/跨设备/可追溯"的 **v1 方向**，本成品未实现——第 4、10 节保留为 v1 设计草案，当前以 IndexedDB（§7.5）替代。

## 4. 数据库设计（v1 草案 · 未实现）

> ⚠️ **本节是面向"多用户 / 跨设备 / 可追溯"的 v1 关系型设计草案，当前成品未实现。**
> 已落地的持久化是**纯客户端 IndexedDB**（见 §7.5）：`works`↔`projects`、`snapshots`↔`revisions` 一一对应，
> store action 接口不变，未来需要云端时按本节迁移即可。下文保留作设计参考。

### 4.1 表结构（Postgres DDL）

```sql
-- 项目（元信息，用于列表/状态）
create table projects (
  id            uuid primary key default gen_random_uuid(),
  user_id       uuid not null references auth.users(id),
  title         text not null,
  status        text not null default 'draft',
                -- draft | bible_ready | converting | done | error
  target_format text default 'cn-standard',
  source_meta   jsonb,            -- {novel_title, author, chapter_count}
  created_at    timestamptz not null default now(),
  updated_at    timestamptz not null default now()
);

-- 原文分章（1:N）
create table source_chapters (
  id            uuid primary key default gen_random_uuid(),
  project_id    uuid not null references projects(id) on delete cascade,
  chapter_index int not null,
  content       text not null,
  unique (project_id, chapter_index)
);

-- bible（1:1，JSONB——本身就是结构化文档）
create table bibles (
  project_id    uuid primary key references projects(id) on delete cascade,
  data          jsonb not null,   -- 符合 Bible schema
  confirmed     boolean not null default false,
  updated_at    timestamptz not null default now()
);

-- 剧本成品（1:1，整份 Screenplay）
create table screenplays (
  project_id     uuid primary key references projects(id) on delete cascade,
  data           jsonb not null,  -- 符合 Screenplay schema
  schema_version text not null default '0.1',
  updated_at     timestamptz not null default now()
);

-- 修订历史（v1：承接 §7.4/§7.5 的 IndexedDB 快照，整本 JSONB）
create table revisions (
  id          uuid primary key default gen_random_uuid(),
  project_id  uuid not null references projects(id) on delete cascade,
  snapshot    jsonb not null,
  note        text,
  created_at  timestamptz not null default now()
);
```

### 4.2 为什么 bible / screenplay 用 JSONB 而不全量拆表

数据本身已经是一份**有 Zod schema 约束的结构化文档**，整存整取最自然：

- **整读整写**：编辑器是对整份 YAML 操作的，存成一坨 JSONB 避免每次 load 都 join + 重排 scenes/elements 再拼回。
- **schema 真源在 Zod**，不在数据库——不想维护两套结构定义。
- **仍可查**：真要做戏量统计等，Postgres 能用 jsonb path 查询；或干脆客户端从 JSONB 算（数据量小）。
- **只把"跨项目要查/列表的字段"放成列**（title、status、updated_at、user_id），其余进 JSONB。

> 取舍：**不做全量规范化**（scenes/elements 各一张表）。仅当未来要跨项目做重关系型查询/分析时再拆。MVP 阶段拆表是负收益。

### 4.3 RLS（行级权限）

```sql
alter table projects enable row level security;
create policy "own projects" on projects
  for all using (user_id = auth.uid()) with check (user_id = auth.uid());

-- 子表通过项目归属校验
alter table source_chapters enable row level security;
create policy "own chapters" on source_chapters
  for all using (exists (
    select 1 from projects p
    where p.id = source_chapters.project_id and p.user_id = auth.uid()
  ));
-- bibles / screenplays / revisions 同理
```

### 4.4 原文存储

3+ 章约几十 KB，放 `source_chapters.content`（TEXT）即可。**长篇**（几十万字）再迁到 Supabase Storage 桶按章存对象，DB 只留引用——呼应长篇 RAG 的 stretch 方向。

## 5. API 契约

所有路由 `runtime='nodejs'`、`maxDuration=60`、`force-dynamic`，请求体用 `lib/api-schema` 的 Zod 校验（含输入限长），并经 `lib/llm/rate-limit` 限速、生产错误脱敏。作品/版本数据**不入服务端**——全在客户端 IndexedDB。

| Method · Path | 入参 | 出参 | 说明 |
|---|---|---|---|
| `POST /api/extract-bible` | `{novel, bibleDoc?}` | `{bible}` | Phase1 反推 Bible（非流式） |
| `POST /api/convert-chapter` | `{chapter, bible, runningSummary, settings}` | `{unit}` | **转单章**（见 §8） |
| `POST /api/update-summary` | `{prevSummary, chapter}` | `{summary}` | 更新滚动摘要 |
| `GET /api/smoke-convert` | `?length=&mode=&brief=` | 整本结果 | 演示端点：**生产返回静态 mock**，dev 实跑 |

> 把 `convert-chapter` 与 `update-summary` **拆成两个端点**：每次调用各自稳在 serverless 60s 内，避免"转换+摘要"合并撞线（§8）。`convert-chapter` 只回 `unit`，摘要由 `update-summary` 单独产出。

### 5.1 契约示例（请求/响应同源 Zod）

```ts
// lib/api-schema.ts —— 入口在 route handler 边界 parse；与业务 schema 同一份 Zod
const ChapterReq = z.object({
  index: z.number().int().positive(),
  title: z.string().max(200).optional(),
  text: z.string().min(1).max(CHAPTER_TEXT_MAX),   // 输入限长，挡超长直怼 LLM
})
const ReqSchema = z.object({
  chapter: ChapterReq,
  bible: Bible,                                     // 复用业务 schema（含 id 唯一性 superRefine）
  runningSummary: z.string().max(SUMMARY_MAX).default(''),
  settings: SettingsReq,                            // 四维度（含自由档 adaptationBrief）
})
```

- 入口 `ReqSchema.safeParse(body)`——**契约违约在边界即返回 400**（长度类错误回显中文提示），坏数据不流进 pipeline。
- 这些 request schema 与业务 schema（`Bible` / `Unit` 等）**同一份 Zod**，不维护两套。

## 6. 后端：pipeline 编排

`lib/pipeline` 是一串纯函数（workflow，非 agent，见产品文档 §3.4）：

```
segmentChapters(text)                          → Chapter[]
extractBible(chapters)                         → Bible            (Phase 1)
─ 作者确认 ─
buildContext(bible, chapter, rollingSummary)   → PromptContext    (常驻+选择性世界书装配)
convertChapter(ctx)                            → Unit             (Phase 2，逐章)
updateSummary(prev, unit)                      → nextSummary      (滚动记忆)
assemble(units, bible, meta)                   → Screenplay
validate(screenplay)                           → Result | RepairLoop
```

`lib/llm` 服务层职责：
- **provider 客户端**：DeepSeek（OpenAI 兼容 `openai` SDK，baseURL `https://api.deepseek.com`）。**强制非思考**（`thinking:{type:'disabled'}`，结构化活不需要思维链，且让 `temperature` / `tool_choice` 生效）。
- **结构化输出 = 强制 function-calling**：单工具 + `tool_choice` 锁定，`callStructured` 直接拿工具入参 JSON 字符串；`callText` 走自由文本（滚动摘要）。截断（`finish_reason==='length'` 且入参不可解析）即 fail-fast。
- **prompt caching**：稳定前缀（schema/指令 + 常驻 world info + 核心 bible）放最前命中 DeepSeek 前缀缓存（§6.1）。
- **校验-修复 loop**：Zod `safeParse` 失败 → 把错误回灌给模型让其修，最多 2 次（详 §6.2）。

### 6.1 prompt caching 分层（稳定前缀命中缓存）

把 prompt 按"变化频率"从低到高分层，**稳定层放最前**；逐章转换时稳定层走缓存命中，只为变化层付费：

```
[L0 系统指令 + 输出 JSON schema]            ← 全程不变
[L1 常驻世界书（constant world info）]       ← 全程不变
[L2 核心 bible（角色 id 清单 / 世界观摘要）]  ← 整本不变
────────── 以上为稳定前缀（命中缓存）────────────
[L3 本章选择性世界书（keyword 命中追加）]     ← 每章变
[L4 滚动摘要 rollingSummary]                ← 每章变
[L5 本章正文]                               ← 每章变
```

- 第一章付全价并写入缓存；后续章 L0–L2 命中缓存，只为 L3–L5 付费——章数越多省得越多。
- 推论：**L2 的 bible 摘要必须在整本转换期间稳定**（不可中途变更角色 id），否则缓存失效。这也是"bible 以服务端/会话态为准、不接客户端传入"的成本动因。

**实战（DeepSeek 自动前缀缓存）**：DeepSeek 没有 Anthropic 的显式 `cache_control`，而是**自动按请求的最长公共前缀**命中——所以"分层"必须**落实到 prompt 字符串的实际拼接顺序**：第一个与上次不同的 token 之后，全部 miss。

- **踩过的坑**：`convertChapterUser` 一度把 L3（本章选择性世界书，每章变）拼在了 L1/L2 之前，于是稳定的全角色清单/世界观排在"每章变"的块**后面**，前缀在第一段就被击穿，convert 调用几乎全 miss。
- **修法**：`assembleWorldInfo` 拆出 `constantBlock`（L1/L2，跨章稳定）与 `selectiveBlock`（L3，每章变）；`convertChapterUser` 严格按 **[稳定：世界观 + 封闭清单 + 设置] → [变化：选择性角色 + 摘要 + 正文]** 拼接。设置（体量/改编自由度）整本不变，归入稳定区。
- **验证**：DeepSeek 响应 `usage` 带 `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens`；`lib/llm/client.ts` 在 dev 下打印每次命中率，第 2 章起 `emit_unit` 应明显跳升。
- **结构性 miss 不必较劲**：`extractBible`（每篇独一份）、滚动摘要（每次都变）、每篇第 1 章（冷启动）天然不缓存；缓存收益主要来自"章数越多、convert 稳定前缀越摊薄"。

### 6.2 校验-修复 loop（让 structured output 一定合法）

```
attempt = 0
raw = generate(ctx)                          # 一次 LLM 调用
while attempt < MAX_REPAIR (=2):
    parsed = Schema.safeParse(JSON.parse(raw))
    if parsed.ok: return parsed.value
    feedback = formatZodError(parsed.error)  # 指明哪个字段路径、期望什么
    raw = generate(ctx + feedback)           # 把错误回灌再生成
    attempt += 1
throw RepairExhausted                        # 交 §9：该章标 error，前端可重试
```

- `MAX_REPAIR` 默认 **2**：足够纠正绝大多数"字段缺失 / 类型错 / 枚举越界"，再多是浪费 token。
- feedback 用 Zod 的 `error.issues`（`path` + `message`），比笼统的"格式不对"具体得多，模型一次就能定位。
- 这是 `extractBible` 与 `convertChapter` **共用**的兜底，封装在 `lib/llm/repair.ts` 的 `withRepair`。

### 6.3 封闭角色 id 注入（禁止就地造 id）

跨章一致性的头号杀手是同一角色在不同章拿到不同 id（"小明" → `char_xiaoming` / `char_ming` / `char_xm`）。对策：

- 转单章时注入**当前已知角色 id 的封闭清单**（来自已确认 bible），指令明确：`dialogue.character` / `characters_present` **只能从清单里选**。
- 遇到清单外的新角色，**不要现编 id**，标记为 `__new__`（或带原文称呼），留待 `assemble` 统一登记。
- `assemble` 末做**引用完整性校验**：任何不在 `bible.characters[].id` 的引用 → 修复 / 回填新角色；仍无法消解则报错（§9 `RefIntegrityError`）。

### 6.4 滚动摘要的 token 预算

`rollingSummary` 随章数增长，必须设上限防 prompt 膨胀：

- **软上限**（如 ~800 token）。`updateSummary(prev, unit)` 每章产出时压缩，保留"角色状态 + 未闭合剧情线 + 关键转折"，丢弃对白细节。
- 超限时优先压最早章节的细节（**近因更重要**），保证最近 1–2 章信息不被稀释。
- 摘要本身也是 LLM 产出，但**无需 Zod 校验**（自由文本），失败重试一次即可。

## 7. 前端架构

**工作台是一个四步向导**（单页内切换，状态存 Zustand）：

```
1 NovelInput   粘贴/上传 + 自动分章预览（bible 文档先行可选区）
2 BibleEditor  展示抽出的 bible，表单可改 → 确认（人在环检查点）
3 Conversion   逐章转换，实时进度条 + 当前章预览
4 Editor       CodeMirror YAML 编辑（实时 Zod 校验）+ ScriptPreview 渲染 + 下载
```

- **状态**：向导步骤、作品库、每作品的 bible/`currentYaml`/快照/断点全在 Zustand store → IndexedDB（无独立服务端数据层，因此不需要 TanStack Query 之类的服务端缓存）。
- **YAML 编辑器**：CodeMirror 6；`onChange` → `js-yaml.load` → `Screenplay.safeParse` → 错误以红波浪线 + 侧栏提示展示。校验通过才允许保存/渲染。
- **渲染**：`lib/render` 是纯函数，客户端把 Screenplay 转成所选 **① 制式**文本（中式 / 好莱坞）预览/下载，无需后端。**四个正交维度**见产品文档 §3.1：① 制式（renderer）/ ② 体量 + ④ 改编自由度（转换前烤进数据的 pipeline 参数）/ ③ 输出格式（导出层）——别混成一个"格式"。
- **持久化真源**：向导步骤、作品库、每作品的原文/`currentYaml`/快照全在 `lib/store/project-store.ts`（Zustand + `persist` → **IndexedDB**，见 §7.5）。

### 7.4 客户端版本管理（整本快照）

服务"可继续打磨"的核心循环。线性快照**随作品持久化到 IndexedDB**（每个 `Work` 自带 `snapshots`），跨刷新留存、单机不跨设备、无 Auth，**不是版本树**。

**快照模型**：

```ts
type Snapshot = {
  id: string                          // snap_<seq>，由单调计数器生成
  label: string                       // 自动生成或手动命名
  origin: 'convert' | 'edit' | 'regen'
  yaml: string                        // 该时刻整本 YAML（快照真源）
  valid: boolean                      // 打快照时 Zod 是否通过 → 红/绿点
  createdAt: number
}
// 每个 Work 自带：{ currentYaml, snapshots: Snapshot[], seq: number }
// 作品库 store：{ works: Record<id, Work>, activeWorkId, step }（见 §7.5）
```

**关键工程点**：

- **id 用单调 `seq`（只增不减），不用 `snapshots.length`**：上限保护会删快照，数组长度非单调，用长度当编号会在删除后**复用 id** → 回滚命中错误版本、React `key` 冲突。`seq` 存进 store，每打一个快照 +1。
- **回滚防丢**：`rollback(id)` 先把当前态另存一份 `edit` 快照，再把 `currentYaml` 换成目标，避免丢掉未保存的编辑。
- **上限滚动**：最多留 N（20）个，超出优先丢最旧的 `convert/regen` 自动快照，保留手动 `edit`。

**触发时机**：③ 整本跑通 → 自动 `convert`；④ 手动「存为快照」→ `edit`；单章重生 → `regen`。

**版本粒度 = 整本，不做单章版本**：章节经滚动摘要逐章串行依赖，脱离前序摘要链的"单章版本"无意义（角色状态 / 剧情进度对不上）。**单章重生的下游脏数据 MVP 不自动处理**——重生第 N 章只把新章替换进 `currentYaml` + 打一个 `regen` 快照，是否重生下游交作者判断；"下游标黄提示 / 级联自动重生"留 v1。

> **v1 升级**：IndexedDB 快照迁到 §4.1 `revisions` 表，即可跨设备/可追溯（详见 §7.5）。store 接口（`snapshot` / `rollback`）不变，只换底层存储。

### 7.5 持久化与作品库（IndexedDB，单用户）

MVP 砍掉多用户/Auth，于是持久化可以做得很轻——**纯客户端 IndexedDB，无后端、无账户**。

- **为什么 IndexedDB 而非 localStorage**：多作品 × 多快照（每快照存整本 YAML）很快超过 localStorage 的 ~5MB；IndexedDB 容量大得多。
- **store 形状**：`{ works: Record<id, Work>, activeWorkId, step }`。一个 `Work` = 一部作品（`title` / `status` / `settings`（四维度）/ `novel` / `currentYaml` / `snapshots` / `seq`）。
- **落盘**：`zustand/middleware` 的 `persist` + `createJSONStorage`，storage 适配器包 `idb-keyval`（`get/set/del`）。**SSR 守卫**：`typeof indexedDB === 'undefined'` 时 no-op，避免 Next 预渲染崩。
- **多作品操作**：`createWork` / `openWork` / `closeWork` / `deleteWork` / `listWorks`（按 `updatedAt` 倒序）。无活动作品 → 作品库列表；选中 → 四步向导。
- **性能注意**：`currentYaml` 每次编辑都写会触发整库序列化，实现时对编辑写入**防抖**，快照/切步才即时落盘。

> **v1 升级**：IndexedDB 换成 §4 的 Supabase（Postgres + Auth + RLS）即得跨设备/多用户/可追溯，`works`→`projects` 表、`snapshots`→`revisions` 表，store action 接口不变。

## 8. 长任务 / 流式 / 进度（关键工程点）

**问题**：多章转换是长任务，可能几十秒到数分钟，而 Vercel serverless function 有超时上限（按计划 60s~300s）。一个请求里串完所有章节会超时。

**方案（MVP 采用）——客户端编排的"逐章请求"**：

```
client 拿到 chapters + 已确认 bible
for i in chapters:
    POST /api/convert-chapter {projectId, i, rollingSummary}
        → 服务端转这一章 → 返回 {unit, nextSummary}
    client: 进度+1，更新 rollingSummary，增量写库
组装完成 → 标记 status=done
```

好处：
- **每个请求只转一章**，稳在超时上限内；
- 进度天然、可视；
- **可断点续跑**：某章失败，重试该章即可，不必从头；
- 与"分章 + 滚动摘要"架构天然契合。

> 明确不做：后台任务队列 / worker（Inngest、Trigger.dev 之类）。对 MVP 是过度工程；逐章请求已够。长篇再考虑队列。

## 9. 错误处理与一致性

- **LLM 产出非法**：Zod `safeParse` 失败 → 修复 loop（§6.2），耗尽则该章标 `error`，前端提示重试。
- **部分失败**：已转的 unit 已落（v1 入库 / MVP 落 IndexedDB），断点续跑，不丢进度。
- **保存冲突**：(v1) 编辑器保存用 `updated_at` 乐观锁；冲突时提示。MVP 单会话无并发，不涉及。

### 9.1 错误分类与重试矩阵

| 错误类 | 触发 | 处理 | 可重试 |
|---|---|---|---|
| `ValidationError` | LLM 产出 Zod 失败 | 修复 loop（§6.2），耗尽 → 标章 `error` | 是（自动 ≤2 次） |
| `RefIntegrityError` | assemble 发现引用不在 bible | 回填新角色 / 修复，仍失败报错 | 半自动 |
| `LlmTransientError` | 限流 429 / 超时 / 5xx | 指数退避重试该章 | 是（≤3 次） |
| `TimeoutError` | 单章超 `maxDuration` | 逐章架构天然隔离，重试该章 | 是 |
| `ParseError` | 非 JSON 输出 | 并入修复 loop 当一次失败处理 | 是 |

> 逐章架构（§8）的红利在此兑现：任何单章失败只影响该章，已转 unit 不丢，**断点续跑**而非从头再来。

### 9.2 状态机（精确转移）

```
draft ──(extract-bible 成功)──▶ bible_ready
bible_ready ──(作者确认 bible)──▶ bible_ready·confirmed
bible_ready·confirmed ──(开始转换)──▶ converting
converting ──(每章成功)──▶ converting              # 自循环，进度 +1，更新 rollingSummary
converting ──(全部成功 + assemble 校验过)──▶ done
converting ──(某章修复耗尽)──▶ error
error ──(重试该章成功)──▶ converting
done ──(编辑器修改 / 回滚)──▶ done                  # 只动 currentYaml + 快照，不回退状态
```

- MVP：`status` 存 Zustand；v1：落 `projects.status` 列（§4.1）。
- `done` 是稳定态：后续编辑、版本回滚都不改 `status`，只在 §7.4 的快照层流转。

## 10. 环境、安全、部署

- **环境变量**：`LLM_API_KEY`（**仅服务端，绝不加 `NEXT_PUBLIC_` 前缀**）、`LLM_BASE_URL`、`LLM_MODEL`；可选 `LLM_THINKING`（默认非思考）、`LLM_RATELIMIT_PER_IP` / `LLM_RATELIMIT_WINDOW_MS` / `LLM_DAILY_CAP`。无 Supabase / 账户相关变量。
- **安全层（公开部署）**：
  - **限速** `lib/llm/rate-limit.ts`：单 IP 滑动窗口 + 全局每日上限（env 经有限正数校验，dev 不限速）。三个 LLM 路由入口拦截，超限 429。
  - **错误脱敏**：生产 500 回通用文案、详细写服务端日志；400 只回显长度类中文提示。
  - **演示端点 mock**：`smoke-convert` 在 `NODE_ENV==='production'` 直接返回预置静态结果，**不触发付费 LLM**；真实生成只在客户端"上传→生成"流程发生（受限速保护）。
  - **输入限长**：`lib/api-schema` 对小说/单章/摘要设上限，挡 MB 级滥用。
- **部署**：Vercel 连 GitHub 自动部署，`runtime='nodejs'`、`maxDuration=60`。不配 `LLM_API_KEY` 也能跑——站点与《雾港》示例纯静态，仅"真实生成"需要 key。

| Day | 工程产出 |
|---|---|
| 1 | `lib/schema.ts`（Zod）、Next.js 骨架、`lib/llm`（接一家 + prompt cache）、`lib/pipeline`（`segment` / `extract-bible`）、Phase1 跑通 |

| 3 | 前端四步向导（含**四维度选择器**）、CodeMirror + 实时 Zod 校验、`lib/render`（**中式 + 好莱坞** + 切换）、**版本管理（§7.4）**、**IndexedDB 持久化 + 多作品库（§7.5）**、修复 loop、部署。Day 3 偏满，持久化/多作品有安全降级线 |

**工程细化（已纳入设计）：**
- **逐章循环是串行**：每章依赖上一章的滚动摘要，故 `convert-chapter` 顺序执行、不可并行（并行会破坏连贯性）。
- **bible 以服务端为准**：转换时从存储（3 天版为活动作品态）按 workId 取 bible，不接客户端传入，保证 id 权威与一致性（也是 §6.1 prompt cache 不失效的前提）。
- **版本管理：IndexedDB、整本快照**：id 用单调 `seq`；回滚先自存防丢；单章重生只打 `regen` 快照、下游脏数据交作者（§7.4）。
- **四维度**：②`lengthForm` + ④`adaptationMode` 转换前烤进数据；①`style` 进 renderer、③`exportFormat` 进导出（自由）。

> 多用户 / Auth / 云端 DB（§4、§10）属 v1；3 天版用 **IndexedDB**（§7.5）做单用户持久化 + 多作品 + 客户端逐章请求替代。

## 12. 明确取舍（不做）

- 不全量规范化数据库（bible/screenplay 用 JSONB）。
- 不上后台任务队列（用客户端逐章请求）。
- 不做实时协作 / 多人编辑。
- 不做服务端渲染各格式（渲染在客户端，纯函数）。
- **MVP 不做多用户 / Auth / 云端 DB** —— 单用户纯本地 IndexedDB；多租户/登录/跨设备留 v1（届时 Supabase Auth + RLS）。
- LLM provider 做抽象但只接一家即可，不提前做多模型路由。
- 版本管理做 **IndexedDB 整本快照**（含 diff 高亮对比）；不做版本树 / 单章版本（§7.4，留 v1）。
