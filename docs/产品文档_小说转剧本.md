# 小说 → 结构化剧本（YAML）工具 · 产品文档

> 产品名：**折幕（Zhémù）** —— "一折一幕"，把小说折成一幕幕剧本
> 版本：v0.1

---

## 1. 背景与定位

小说改编成剧本是个又繁又慢的活：要改格式、重排台词和场景、统计角色戏量，跨章节还得手动保持人名、设定、剧情的连贯。本工具用 AI 把这件事自动化，**把 3 章以上的小说自动转成结构化剧本（YAML），让作者快速拿到一份可编辑、可继续打磨的初稿。**

- **目标用户**：网文 / 短剧 / 严肃文学作者，以及做 IP 改编初筛的小团队。
- **一句话定位**：不是"给人看的剧本文本"，而是"一份人能改、机器也能用的结构化剧本数据"。

---

## 2. 竞品与差异化

| 产品 | 定位 | 输出形态 | 局限 |
|---|---|---|---|
| 海马轻帆 | to B 影视剧本基础设施 | 剧本格式**文本**（支持中式/好莱坞切换） | 停在"给人读的文本"，无结构化数据；意识流/情节量不足的小说转得差 |
| LivingWriter | to C 写作 IDE | 逐章转剧本，存原章节下方 | 锁定写作平台内部；偏写作辅助 |
| 量子探险 | 短剧流水线 | 章节→剧本→配音→视频 | 偏成品产出，结构不透明 |

**我的差异点：**

1. **结构化 YAML 作为中间表示（IR）** —— 内容与格式分离。一份 YAML（数据真源）可换**制式**渲染成中式 / 好莱坞，再换**输出格式**导出纯文本；也能被下游工具（戏量统计、配音、分镜）直接消费。（制式 / 体量 / 改编自由度 / 输出是四个正交维度，见 §3.1）
2. **跨章节一致性** —— 分章处理 + 章节间传递 running state（角色 + 剧情摘要），解决竞品普遍做不好的连贯问题。
3. **Story Bible 双向** —— 世界观 / 人设 / 大纲既可由作者输入（grounding），也可由 AI 从小说反推、交作者确认。

## 3. 核心设计

### 3.1 内容 vs 格式：四个正交维度

「输出多种格式」其实是 **4 个互相正交的维度**，混成一个"格式"列表是设计陷阱：

```
小说原文
   │  ② 体量(电影/竖屏短剧/剧集) + ④ 改编自由度(忠实/平衡/自由)   ← 烤进数据，转换前定
   ↓  AI pipeline
内容层 = YAML(真源，记"是什么")
   │  ① 制式(中式/好莱坞)                                       ← 纯渲染，数据不动，随时切
   ↓  renderer
样式化文本
   │  ③ 输出格式(YAML/纯文本)                                   ← 导出层
   ↓  export
交付物
```

| 维度 | 选项 | 何时选 | 性质 |
|---|---|---|---|
| ① 制式 | 中式 / 好莱坞 | 默认转换前给，编辑器可随时切 | 自由（数据不动） |
| ② 体量 | 电影 / 竖屏短剧 / 剧集 | 上传后、转换前 | **烤进数据**（改了要重转） |
| ④ 改编自由度 | 忠实 / 平衡 / 自由（**自由**档可附自定义改编要求 `adaptationBrief`） | 上传后、转换前 | **烤进数据** |
| ③ 输出格式 | YAML / 纯文本 | 导出时 | 自由 |

YAML 是唯一真源，永远不动；**②④ 在生成时定**（改了要重转），**①③ 是生成后的自由下游变换**。这就是为什么能一键切中式/好莱坞——内部是一份结构化数据 + 多个 renderer。

> ④ 的"自由"档进一步支持一句**自定义改编要求**（如"把背景改到近未来赛博都市，人物关系与主线保留"），它会注入转换 prompt，让产物按要求重塑世界观，同时不破坏闭合角色清单与引用完整性。

### 3.2 两层 Schema：Bible 层 + 场景层

- **Bible 层（项目级）**：标题、logline、世界观/设定、角色表、大纲结构。
- **场景层（内容级）**：场景（标题：内/外、地点、时间）→ 元素（动作描述 / 台词 / 角色 / 括号提示 / 转场）。

> Bible 层的字段**既可作输入、也可作输出**：作者有就喂进去当背景；只有成稿就由 AI 反推填入，再交作者确认。同一套结构，两个方向。

### 3.3 一致性引擎（分章 + 世界书注入 + 滚动摘要）

底层一律分章（短篇无章节则按长度切）。跨章一致性靠三件事，借鉴"世界书（World Info）"注入模型：

- **Bible 作为世界书**：每个角色/设定/线索是一个 entry，分两类注入——
  - **常驻 entry（constant）**：核心世界观、logline、幕结构，每次都注入、永不丢，框定整个世界观。
  - **选择性 entry（keyword-triggered）**：只注入当前章里实际出现的角色/设定，避免 context 臃肿。
- **滚动摘要（rolling summary）**：每转完一章更新一份"到目前为止发生了什么"的压缩摘要，下一章带上它，模型不必重读全部前文。这就是轻量的"记忆"——不需要向量库或重型 memory 子系统。
- **bible 先行 → prompt caching**：bible/常驻 world info 是稳定内容，放在每次调用的最前面即可命中 DeepSeek 的前缀缓存，第一章付全价、后续章节走缓存价。

**每章 prompt 装配结构**（稳定在上、易变在下 → 高缓存命中 + 设定不丢）：

```
┌─ 可缓存前缀（稳定，走 cache）──────────────┐
│  schema/指令 + 常驻 world info + 核心 bible │
├─ 慢变 ──────────────────────────────────┤
│  滚动摘要（到上一章为止）                    │
├─ 每章变 ────────────────────────────────┤
│  本章 keyword 命中的选择性 entry            │
│  当前章节原文                               │
└────────────────────────────────────────┘
```

> 说明：对**结构化的 bible**，世界书式关键词注入比 embedding RAG 更合适也更简单，所以它替代了 RAG 在 bible 上的用途；embedding RAG 仅在"长篇小说原文本身塞不下"时用来检索 prose（见 §5 stretch）。

### 3.4 编排：现在是 workflow，留好 agent 升级路径

本系统的步骤是**已知且固定的 DAG**（抽 bible → 确认 → 逐章转 → 组装），因此用**编排好的 workflow（prompt chain）**实现，而非 autonomous agent。

- **为什么不直接上 agent**：路径已知时，agent 的控制循环、tool 定义、防死循环 guard、非确定性容错都是纯脚手架，买不到收益；且非确定性会让输出不可复现、demo 不稳、debug 更难。
- **为什么 workflow 是地基而非过渡品**：每一步写成干净的 step 函数（抽取/注入/转换/校验），将来升级时这些 step 直接变成 agent 可调用的 tool，上面加 controller 即可，step 实现几乎不动。
- **升级谱（由轻到重，后期按需推进）**：
  1. 自检-修订 loop（转完→对 schema/质量 rubric 自评→改）——仍基本是 workflow
  2. 给模型若干 tool（检索历史 / 一致性检查 / 向作者提问），由它临场决定调用——ReAct 式 agent
  3. 多 agent（改编 / 续连检查 / 格式）协作

## 4. 核心流程

```
1. 输入：bible 文档先行（世界观/人设/大纲，可选）→ 再粘贴/上传小说（3+ 章）
2. Phase 1 抽取：作者无 bible 时，AI 读小说 → 反推 bible → 填进 YAML bible 层
3. 检查点：作者查看 / 编辑 / 确认 bible（人在环里）→ 确认后的 bible 作为世界书框定全程
4. Phase 2 转换：常驻+选择性 world info + 滚动摘要 + 本章原文 → 逐章转场景 → 组装完整 YAML
5. 输出：YAML 预览 + 在线编辑 + 下载；一个 renderer 剧本预览
```

## 5. 功能清单

**已交付（核心能力）**
- 小说 → 结构化 YAML 的转换 pipeline（分章 + 跨章 state）
- Zod schema（结构真源）+ Schema 设计文档（说明每个设计为什么这么定）
- YAML 预览 + CodeMirror 在线编辑（实时 Zod 校验）+ 导出（YAML / 纯文本）
- 强制 function-calling 出 JSON → Zod 校验 → `withRepair` 失败自修复
- 单用户持久化 + 多作品库（纯客户端 **IndexedDB**，无 auth）
- 版本管理（整本快照 + 回滚）+ **版本 diff 高亮对比**（绿增 / 红删）
- Bible 两段式：AI 抽取 → 作者确认 → 再转换
- **双制式 renderer：中式 ↔ 好莱坞**（纯函数，同数据换 slug/排版，编辑器随时切——"内容/格式分离"的招牌 demo）
- **四维度选择器全开**：① 制式 + ② 体量（电影/短剧/剧集）+ ④ 改编自由度（忠实/平衡/自由，**自由**档带自定义改编要求）+ ③ 输出格式
- **逐章断点续跑**：长篇转到一半失败不丢前面的章，重试从断点继续
- 安全：真实生成路由内存限速（单 IP 滑窗 + 全局日上限）、输入限长、生产错误脱敏、演示端点生产走静态 mock
- 一键《雾港》示例：体量×3 + 改编×3（含"自由·赛博"自定义改编）

**后续 / 未做（v2，展示扩展性）**
- PDF 导出（③ 输出格式再加一种 renderer 即可）
- 长篇 embedding RAG：仅用于长篇**原文** prose 塞不下时的检索（bible 已由世界书覆盖）；retriever 接缝已留
- 自检-修订 loop / agent 化升级（见 §3.4 升级谱）
- 角色戏量统计等下游分析（演示"结构化的价值"）

## 6. 技术栈

按已熟悉的栈来，不引入学习成本：

| 层 | 选型 | 理由 |
|---|---|---|
| 前端框架 | **Next.js 14 (App Router) + TS** | 单仓库前后端，API routes 跑服务端 LLM 调用，key 不暴露 |
| UI | **Tailwind + Radix UI**（野兽派/硬描边直角） | 快速搭、组件现成；硬描边风格专业且有辨识度 |
| LLM 编排 | **手写 TS prompt chain**（逐章客户端编排） | 不上 LangChain，更能体现对 workflow 的掌控；chain 模式正合"分章 + state" |
| 结构化输出 | 强制 **function-calling** 出 JSON → **Zod** 校验 → `withRepair` 失败自修复 → **js-yaml** 序列化 | function-calling 比自由出 YAML 可靠；Zod 当结构真源 |
| Schema 真源 | **Zod** | TS-first，可推导 JSON Schema 和文档 |
| YAML 编辑器 | **CodeMirror 6** | 比 Monaco 轻，带实时解析校验 + 版本 diff |
| 持久化 | **纯客户端 IndexedDB**（Zustand persist + idb-keyval） | 单用户、无 auth、多作品库 + 版本快照 + 断点续跑 |
| 模型 | **DeepSeek**（OpenAI 兼容，`openai` SDK，强制非思考） | 结构化输出稳、性价比高；非思考让 tool_choice 与 temperature 生效 |
| 部署 | **Vercel** | 一键（生产演示端点走静态 mock、真实生成带限速） |

## 8. 交付概览

- **范围取舍**：不做多用户 / Auth / 云端 DB——用纯客户端 **IndexedDB** 做单用户持久化 + 多作品库，省下整块后端与鉴权。
- **端到端**：导入小说 → AI 反推并确认 Bible → 逐章转换（封闭角色清单 + 世界书注入 + 滚动摘要）→ 组装并引用完整性校验 → YAML 编辑 / 切制式 / 导出。
- **工程细节**见 [技术设计文档（工程侧）](技术设计文档_工程侧.md)：DeepSeek 客户端、逐章客户端编排、prompt 前缀缓存、`withRepair`、限速与错误脱敏、断点续跑。

## 9. 风险与取舍

- **长篇 context 上限**：主攻 3+ 章（一口吞得下），长篇靠 retriever 接缝 + embedding RAG 扩展，核心不依赖它。
- **转换质量取决于原文**（意识流 / 情节量不足的小说转得差）：用 bible grounding + 世界书注入 + 作者确认环节缓解。
- **编排选 workflow 而非 agent**：路径已知，workflow 更稳、可复现、易 debug，且是 agent 的地基（step → tool）。
- **明确不做（v2）**：多用户 / Auth / 云端 DB；PDF 导出；embedding RAG 当核心依赖；autonomous agent；复杂文档解析器（bible 文档直接当 context 注入）；世界书只做最小版（constant + keyword 选择性注入），不做递归 / depth / 概率全家桶。

## 10. 验收标准

1. 能把一篇 3+ 章小说转成 **schema-valid** 的 YAML，且跨章人名/设定连贯。
2. 作者能在线编辑 YAML 并下载。
3. 附一份 Schema 文档，**说清楚每个设计为什么这么定**（这是交付重点）。
